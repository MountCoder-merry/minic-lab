## 源码阅读顺序

源码均在 src/main/java/edu/minic 下：

1. core/Source.java 与 core/Syntax.java：诊断、Token、Span、类型和 AST。
2. core/CompilerService.java：编译总入口及阶段停止条件。
3. core/Lexer.java：最长匹配与注释扫描。
4. core/Parser.java：语句递归下降、表达式优先级及同步恢复。
5. core/Semantic.java：签名预注册、Scope 链、Flow 集合、属性。
6. core/Ir.java：四元式、短路、参数顺序和优化。
7. core/Bytecode.java 与 core/VirtualMachine.java：局部槽、标签回填、指令与调用帧。
8. lab/Automata.java、lab/Grammar.java、lab/Lr.java：独立算法与分析轨迹。
9. ui/CompilerPanel.java、ui/LabPanels.java：核心结果接入和后台任务管理。
10. src/test/java 中的测试：先看输入与预期，再回溯相应算法。

## 常见问答

**为什么这仍是编译器？**

前端真实翻译出目标指令，VM 执行的是目标指令。采用虚拟机作为目标架构，与直接解释 AST 是两种实现路径。

**与完整 C 有何区别？**

语法相似但语言规则由 SPEC 定义。这里强类型区分 bool/int，分支和循环强制大括号，没有指针、数组、全局变量和 C 标准库。

**为什么不全部使用 LR 分析主语言？**

主编译器选择容易定位与讲解的递归下降；LR 实验提供通用构表与冲突分析，两者复用形式化概念但不伪称同一个分析引擎。

**内外层 x 为什么不会冲突？**

查找从当前 Scope 向外进行。同名变量绑定不同 Symbol.id 和局部槽，IR 使用唯一编号，不使用裸名字。

**递归为何不会覆盖旧变量？**

每次 CALL 分配新的 Frame，局部槽数组和操作数栈均独立。RET 返回到调用者保留的 PC。

**为什么 while 内赋值仍可能报未初始化？**

循环可能执行零次。没有额外控制流证明时，循环出口只能保留进入循环前已确定赋值的变量。

**为什么 1/0 没有在优化时直接报错？**

它可能位于短路跳过或不可达分支。优化保留该运算，只有实际执行到它才报告运行错误，输出顺序与未优化版本保持一致。

**SLR(1) 与 LR(1) 的区别？**

SLR 用整个非终结符的 FOLLOW 控制规约，规范 LR(1) 为每个项目保存上下文相关展望符。可复制下面的文法，输入串填写 `* id = id`，演示 SLR 冲突而 LR(1) 无冲突：

```text
S -> L = R | R
L -> * R | id
R -> L
```

**如何证明不是硬编码状态表？**

修改文法或正则，重新构造并观察状态和表变化。自动测试还核对不同文法、空串、拒绝串与冲突；状态编号可以不同，但项目内容和识别行为必须正确。

**实现了哪些优化？**

基本块内常量折叠与临时量复制传播，主要减少运行时计算。没有实现公共子表达式消除、寄存器分配或 SSA；指令数不一定减少。

**遇到分析表冲突怎么办？**

显示全部动作/候选式并停止歧义分析，说明文法不适用于当前方法。不能偷偷默认移进或默认规约来伪装成功。
